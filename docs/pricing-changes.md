# 计费计划与时间轴版本管理

以当前代码为准。设计讨论见 [调价计划与修改记录设计](superpowers/specs/2026-11-24-scheduled-pricing-design.md)。

## 1. 正式术语与三层模型

整店计费统一按 **计划 → 方案 → 时段** 三层命名（供文档、产品沟通与后续开发对齐）：

| 正式名称 | 含义 | 代码 / 数据对应 |
| --- | --- | --- |
| **计划** | 时间轴上的每一个节点——一家店在某一刻起生效的完整计费配置（包含这一刻全部的**方案**以及全部**资源计费**绑定：资源组、资源专属方案、桌游对局方案）。按时间分为**以前的计划**（历史只读）、**现在的计划**（生效中）、**未来的计划**（待生效，到点自动切换）。 | `pricing_changes` 行与 `PricingSnapshot` |
| **方案** | 一份计划里的一条计费方案（按时计费 `time.priority`、固定收费 `charge.fixed`、消费封顶 `time.cap`）。方案在某份计划中可编辑、停用，或从该计划移除（底层以 `status='archived'` 软归档保留，以便历史计划和账单继续引用）。 | `pricing_configs` 行与 `PricingConfig` |
| **时段** | 按时计费或消费封顶方案内部的时间分段（星期、指定日期、钟点、单价、宽限、时段封顶、优先级）。 | `provider.rules` |

- **计划来源 `source`**：`edit`（对现在计划的修改）、`schedule`（未来计划到点生效或「立即生效」）、`restore`（由历史计划覆盖或派生）、`import`（数据导入）、`history`（本表引入之前的历史发布，或首次修改前的基线）。
- **未来计划**：生效时刻在未来、尚未执行的计划（`status='pending'`），保存**完整的目标快照**，到点整体切换。

店里「设时间」只有两处：**时段**里的星期、指定日期、钟点（每天 / 每周重复的日历），以及**计划**的生效时刻（整套计划从哪一刻起切换）。时段上的绝对起止时间（`dateTimeRange`）不再能新建或修改，见 §6。

## 2. 存储

迁移 `0064_pricing_changes.sql`，SQLite 用同一份 `packages/storage-sql/src/pricing-change-schema.ts`。

| 列 | 说明 |
| --- | --- |
| `status` | `pending` / `applied` / `cancelled` / `failed` |
| `effective_at` | 计划的生效时刻（UTC）；直接修改为空 |
| `applied_at` | 实际生效时刻，时间轴按它排序 |
| `release_id` | 生效后的 `pricing_release_heads`：规则内容从不可变版本读出，不另存 |
| `bindings_json` | 生效后的全部绑定 `{ groups, resources, tables }`（规则 ID 或 null）；早期记录为空 |
| `target_json` | 仅 `pending`：完整目标价目（规则按 `pricing_configs` 行的存储形式）与绑定；生效后清空 |
| `notes_json` | 生效时的自动处理说明，见 §4.2 |
| `actor_id` / `actor_name` | 操作人（平台账号 `user:<id>` 或店员 `staff:<id>`），名称取当时的显示名 |

同一店铺同一时刻只能有一个 `pending`（部分唯一索引）。迁移为已有的每个发布版本补一条 `history` 记录（没有绑定、没有操作人）。

## 3. 记录直接修改

`packages/server/src/pricing-changes.ts`：

- 规则的新建、编辑、归档、恢复（`routes/shops/pricing.ts`），资源组改规则（`merchant-resource-groups.ts`），已有资源改专属规则或桌游规则（`merchant-resources.ts`）都会在写入后调用 `recordPricingChange`。
- 第一次记录前，`ensurePricingBaseline` 先把当时的价目记为一条 `history`，后面的记录才有比较的对象（导入的规则、建店时的默认规则都在这里）。
- 同一操作人 10 分钟内的连续直接修改合并为一条。只新增（还没用规则）或删除了资源组 / 资源时，不新增记录，只更新上一条的绑定。
- 记录在修改提交之后单独写入，不与修改同一事务。记录写失败只打日志：下一条记录与上一条已写入的记录比较，这次改动仍会出现，只是合并到下一条里。

### 计划排着时直接修改

完整目标价目到点会覆盖之后的直接修改。为了不悄悄丢掉修改，直接修改后 `syncDirectEdit` 检查每个待生效计划：

- 计划里这一项与修改前的当前值相同（计划没改它）：把这次修改同步进计划；
- 计划本来就改了这一项，或同步后计划不再成立：计划保持原样。接口返回 `pendingConflicts: [{ changeId, effectiveAt, plans, bindings }]`，「计费规则」页显示「到点时会以计划里的版本为准」。

归档规则时，待生效计划里仍绑定或依赖它的也算使用者，返回 `PRICING_CONFIG_IN_USE` 并列出「某时刻的调价计划」。

## 4. 调价计划

### 4.1 保存

`savePricingChange`：先执行已到期的计划，再以「生效时刻的预计价目」（当前价目依次叠加更早的待生效计划）为底，叠加请求里改过的规则和绑定，得到完整目标价目。编辑已有计划时以它保存的目标为底（`note` 省略时保留原备注，传 `null` 清空备注）。目标必须自身成立（`validatePricingSnapshot`：规则完整、关系图成立、未归档规则不依赖已归档规则、绑定的规则能计费）。

保存较早的版本（含 `effectiveAt: null` 的整版批量修改）时，`carryForward` 会把这次改动的规则和绑定同步进更晚的待生效计划里**没有单独改过**的项（更晚版本自己改过的项保持自己的值，并在响应 `pendingConflicts` 中返回），并校验之后的每个计划叠加上去仍然成立，否则返回 `PRICING_CHANGE_BREAKS_LATER`。

`effectiveAt` 为空表示立即生效：保存后马上在一个事务批次里原子执行，仅生成一条记录（未带 `restoredFrom` 时 `source='edit'`，带 `restoredFrom` 时 `source='restore'`），用于批量保存当前价目和从历史版本「覆盖现在」。

### 4.2 生效

`applyPricingChange` 在一个批次里写入所有有变化的规则行、绑定，并把记录改为 `applied`。现有触发器为每行生成版本和发布，批次是一个事务，中间发布不会被入场绑定，记录引用批次结束时的 head。已与目标相同的规则不重写，不会多出版本。重复执行是安全的。

计划保存之后店里的变化由 `reconcilePricingTarget`（`packages/core/src/pricing-snapshot.ts`）处理，写进 `notes_json`，时间轴上显示：

| 情况 | 处理 | 说明 `kind` |
| --- | --- | --- |
| 计划保存后才新建的规则、资源组、资源 | 保留不动 | — |
| 计划里绑定的资源组 / 资源已删除 | 跳过这一行 | `binding-skipped-missing` |
| 桌游有人在桌（与改桌游配置的限制一致） | 不切换这张桌的规则 | `binding-skipped-seated` |
| 计划要归档的规则仍被保留下来的绑定或规则依赖 | 不归档 | `archive-kept` |

处理之后仍不成立时（理论上不会出现），记录改为 `failed`，价目不变，「计费规则」页顶部显示红色提示。

### 4.3 何时执行

不依赖定时器精度，任何一处先到都执行同一个幂等函数：

1. **开始计费前**：`resourceBilling` 的 `planOf`、`preview`、`activate`、`rulesOf`、`admits`（`middleware/tenant.ts`），以及桌游的每次操作与预览（`routes/platform/table.ts`），都先调用 `applyDuePricingChanges`。所以切换时刻之后入场的玩家一定拿到新价目。每个店铺下一次到期时间在进程内缓存 30 秒，平时不增加查询；本进程保存或取消计划时清掉缓存。
2. **读计费规则页、修改记录时**：同上，管理端看到的总是已生效的状态。
3. **整点 cron**（`worker.scheduled`）和本地 Bun 运行时每分钟的定时器：扫描所有到期计划，绕过缓存。

到点时仍在店的玩家沿用入场时锁定的版本，结账后再入场才用新价目（与[计费版本](pricing-versions.md)一致）。被改规则生成新版本后，它的时段封顶从零累计，所以编辑器默认生效时刻为店铺时区次日 00:00，选非零点时会提示。

## 5. 时间轴与恢复

接口在 `/api/v1/shops/:shopCode/staff/pricing-configs/changes`（也挂在 `/pricing/changes`）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/?before=&limit=` | `{ pending, applied, failed, nextBefore, names, bindings, timeZone }`，`bindings` 为当前的计费绑定。`pending` 按生效时刻排序，每条与它要替换的价目比较；`applied` 按生效时间倒序分页（默认 30 条），每条与前一条比较；`failed` 为最近 5 条失败 |
| GET | `/projected?at=` | 该时刻的预计价目 `{ snapshot: { configs, bindings }, names }`，供新建计划 |
| GET | `/:id` | 一条记录的完整价目与改动 |
| GET | `/:id/restore-draft` | 恢复草稿：那时的规则；之后才新建、没有被使用的规则标为归档；那时的绑定（仍存在的资源组 / 资源），早期记录没有绑定时用当前绑定 |
| POST | `/` | `{ effectiveAt: string \| null, plans, bindings, note?, restoredFrom? }`，`plans` 只需包含改过或新建的规则（与编辑规则的请求同形，带 `id`、`status`），`bindings` 只需包含改过的项 |
| PATCH | `/:id` | 修改待生效计划，请求同上 |
| POST | `/:id/cancel` | 取消待生效计划或删除未生效（`failed`）版本，记录保留为 `cancelled` |
| POST | `/:id/apply-now` | 立即生效（更早的待生效计划先执行） |

每条记录的 `items` 是结构化的改动（`PricingChangeItem`）：规则新建 / 归档 / 恢复 / 启停 / 改名，时段增删，时段字段（收费、计费间隔、宽限、封顶、优先级、名称、启停、时间或日期），固定收费金额，依赖与冲突，绑定变化。删除的资源组 / 资源不算改动；新出现的只在已经用了某条规则时算一条绑定变化（从「不计费 / 跟随资源组」改为该规则）。`playersOnIt` 是仍按这条记录的版本计费的未结账玩家数。

错误码：`PRICING_CHANGE_IN_PAST`、`PRICING_CHANGE_TIME_TAKEN`、`PRICING_CHANGE_NOT_PENDING`、`PRICING_CHANGE_NOT_FOUND`、`PRICING_CHANGE_BREAKS_LATER`，以及保存规则的全部校验码。

## 6. `dateTimeRange` 退役

时段的绝对起止时间只来自 prism-neo 导入（一次性的节假日时段）。保存规则（直接修改与调价计划）时，带 `dateTimeRange` 的时段必须与当前版本同 ID 的时段完全相同，否则返回 `PRICING_RULE_DATE_TIME_RANGE_RETIRED`。计费引擎与结算照常读取它：历史版本和未结账入场可能用到。编辑器不再显示这两个输入框，只读显示「旧系统导入的一次性时段」，过期的标「已过期」，整个时段仍可移除。

## 7. 界面

「计费」页（`packages/prism-web/src/ui/merchant/PricingWorkbench.tsx`）把整店计费组织成一条按时间排开的**计划**时间轴，在桌面上是一个紧贴视口的工作台（高度 `100dvh − 8.75rem`，最低 `36rem`），左右两栏各自滚动；窄屏上下排列。店家顶栏把店铺切换器与导航标签合为一行，计费页本身不再单独占一行标题。界面自然使用 **计划 / 方案 / 时段** 措辞，并在计费说明书开头用一段引导自然带出这三层关系。

- **顶部计划时间轴**（`PricingVersions.tsx` 中的 `VersionBar`）：
  - 独立纯粹的水平轨道条（`bg-ink/[0.018]`），每个节点是一枚横向双行圆角卡片，节点之间以独立线段相连（历史为实线、未来为虚线），连线位于卡片外部不穿过卡片。
  - 最左端为「‹ 历史」胶囊按钮，默认折叠历史计划（无历史时禁用），点击展开后从左到右按从旧到新排列并自动滚动保持「现在」在视野内，最左端支持「更早」分页加载；再次点击「收起 ›」收起历史，若当前正查看历史计划则自动回到「现在」。
  - 中间是「现在（生效中）」，右侧按生效时间排开未来计划，轨道末尾接虚线与「+ 未来计划」按钮。
  - 选中哪份计划，下方整个工作台就只显示那份计划的完整方案与资源计费，方案、依赖关系、使用者和改动角标互不串版。
- **计划横幅**（`VersionBanner`）：
  - **现在的计划**：不显示横幅，直接进入工作台，最大化正文纵向空间。
  - **未来的计划**：显示生效时间、备注、操作人、可展开的「相比上一份计划 N 项改动」，以及「改时间与备注」、「立即生效」、「删除此计划」。新建未来计划通过弹窗选生效时间与备注，起点自动继承前一份计划。
  - **未生效（failed）**：显示失败原因，可「删除此计划」。
  - **以前的计划（历史只读）**：标「只读」，可「以此创建未来计划」或「覆盖现在」（立即生效）。
- **整份计划暂存与统一保存**：
  - 在现在的计划和未来计划中，编辑 / 新增 / 移除方案，以及修改资源组 / 资源 / 桌游的计费绑定，都会先暂存到本地草稿（左侧对应条目显示「未保存」标记），不会每改一条就请求接口或生成多条历史计划。
  - **计划内移除（底层归档）**：界面上不再展示「归档 / 显示已归档」，每份计划只列出这一刻实际存在的方案。移除仍被引用的方案会先提示解除绑定或依赖；草稿里刚新建尚未保存的方案直接从草稿删掉；已保存方案在底层记为 `status='archived'` 以保持历史账单与发布快照引用完整（若未来计划里新建后在生效前又移除，差异计算与生效写入都会直接跳过，不留死记录）。想复用过去移除的方案，可展开历史计划并在方案详情点「复制到现在」。
  - 存在未保存修改时，工作台上方显示未保存操作栏（「有 N 项未保存修改」、「放弃修改」、「保存全部修改」）。点击「保存全部修改」后，现在的计划走 `POST /changes`（`effectiveAt: null`）一次原子生效并只生成一条 `edit` 历史计划，未来计划走 `PATCH /changes/:id` 一次写入；若更晚的未来计划改了同一项，右栏顶部提示冲突并可点击跳转。
  - 切换计划或离开页面前，如有未保存修改会先二次确认。
- **左栏**：顶部两个标签「方案」和「资源计费」，按当前选中的计划（含本地暂存修改）显示；底部固定计划内工具栏（「计费模拟器」与「计费说明书」）：
  - 「方案」：可编辑计划顶部显示「添加方案」（历史只读计划无工具栏）。方案按创建时间排列（颜色随位置，保存不会改变顺序和颜色），只展示本计划存在的方案。每条方案显示颜色点、名称、停用标记、未保存或相对上一份计划的变动标记（未保存 / 新增 / 已改）、计费方式与时段数（固定收费显示金额），以及该计划里的使用者（资源组、资源专属方案、桌游；只被其他方案依赖时写「随依赖它的方案计费」，都没有时标「未被使用」）。末尾是「方案关系图」。
  - 「资源计费」：以资源组为一层节点按树形统一列出计费绑定——每个资源组（含默认组与仍存在于版本里的分组）只出现一次并可直接点选设置整组默认方案，其所属的可扫码资源（默认省略无玩家链接的纯 Bot / 纯 IoT 资源，除非已绑定专属方案或有版本变动）缩进排列在对应组下方；若某资源拥有桌游能力，其入场 / 等位方案与对局方案合并展示在同一条资源项下，不再单独重复拆出「桌游」分组，无匹配组时统一归入末尾「未分组」。未保存标「未保存」，相对上一份计划已保存的改动标「已改」。早期未记录绑定的历史计划提示「早期记录没有保存资源计费设置」。
- **右栏**：左栏选中项的详情与编辑，现在与未来计划共用完全相同的界面：
  - 方案详情（`PlanDetail.tsx`）：名称、状态、编辑 / 移除（历史只读计划隐藏写操作，改为提供「复制到现在」）；未被使用时提示不会计费；计费时段表（时段、时间、适用日期、收费、宽限、时段封顶，按优先级排列，归档时段划掉；封顶方案只有封顶金额）；关系与使用（该计划里的使用者、依赖、被依赖、冲突，点方案名切过去）；「这份计划的改动」（只显示当前选中的计划对这条方案做的改动）。时段方案右侧是当日预览圆环。
  - 方案编辑（`Pricing.tsx` 中的 `PricingEditor`）：在右栏内联进行，底部按钮为「完成编辑」，点后暂存到当前计划草稿并回到方案详情，全部改完后由顶部「保存全部修改」统一提交。
  - 资源计费详情：显示所属资源组（资源专属方案选择「跟随资源组」时同时提示当前从所属资源组继承生效的方案），在现在和未来计划里直接下拉切换该资源组或资源的方案；具备桌游能力的资源在同一详情页内分「入场 / 等位方案」和「桌游对局方案」两张卡片一并编辑（均先暂存到草稿，统一保存）；历史计划只读显示，并可跳转到对应方案。
  - 方案关系图：按当前计划（含暂存修改）的绑定展示，点方框切到那条方案。
  - 计费模拟器：位于每份计划内部（左栏底部打开、右栏展示），调用 `POST /pricing-configs/simulate/preview` 并传入当前所选计划的方案快照（支持现在的计划、未来计划、历史计划以及未保存草稿的实时试算）。
- 时间轴接口额外返回当前的计费绑定 `bindings`，列表、方案详情与资源计费标签据此显示使用者与绑定。

## 8. 店铺数据导入

导入会替换规则、版本和发布，修改记录（含待生效计划）随之清空（`shop-data-replace.ts`），下次修改时从导入后的价目重新记基线。导出不包含修改记录。
