# 店铺 JSON 数据备份与迁移

店主在「店铺设置 → 数据管理」下载或导入 JSON。默认导出业务备份，适用于店铺业务数据备份及 beta／正式环境之间迁移。也可以选择仅配置导出。无需新增数据库迁移；两个环境均需部署支持此格式的 Worker，并完成现有 D1／UTC 迁移。

## 范围

| 模式 | 包含的数据 |
| --- | --- |
| 业务备份 | 资产定义、计费效果与方案、礼物与商品；玩家和外部平台身份、前台卡片标识、资产余额与流水、兑换码与兑换记录、会话、账单及保存的时间轴、商品订单、前台收款；完整历史计费版本、发布版本与会话版本绑定 |
| 仅店铺配置 | 资产定义、计费效果与方案、礼物、商品；不包含玩家、财务历史或兑换码；在目标店铺生成新的计费发布版本 |
| 两者共同包含 | 入场／收银开关、注册与身份绑定要求、位置校验开关、入场方案选择、Bot 联系说明、投币冷却时间、新玩家礼物选择 |

来源名称、编号、位置、IANA 时区和环境地址写入文件用于识别。导入保留**目标店铺**的名称、位置、时区、封面及管理员，不改变它们。当前版导出业务范围中的所有状态，包括归档配置、禁用玩家、已结账单及仍在计时的会话。

不导出平台账号、Passkey、OAuth 数据、网页登录账号关联（`web-account`／`shop_player_accounts`／`shop_platform_bindings`）、员工登录凭据、Bot/API 凭据、设备定义和连接密钥、设备在线状态／待执行命令、麻将座位占用、登录会话、绑定码、操作锁及请求去重历史。这不是平台整库备份；平台管理员仍应单独使用 D1 备份保存这些平台及设备数据。

外部平台身份（如 onebot、telegram）和玩家业务 ID 保留。玩家之后通过 Bot 重新绑定时可按原外部身份找到原玩家及余额；网页登录账号关联需重新建立。没有外部身份的玩家不能仅凭显示名称自动关联到新环境账号，避免同名玩家被错误绑定。设备、接入凭据需重新配置。

跨环境迁移前先停止旧环境营业、处理在用设备和未结账单，再导出。目标环境核对余额、规则、历史账单及账号绑定后再营业，避免同一份会话在两个环境继续计费。恢复的历史收款记录仅作为记录，不会发送收款、赠送余额或硬件控制指令。

## 格式及时间、金额

```json
{
  "format": "prism-shop-data",
  "version": 1,
  "scope": "business",
  "exportedAt": "2026-10-06T00:00:00.000Z",
  "source": {
    "publicId": "source-shop",
    "name": "来源店铺",
    "timeZone": "Asia/Shanghai",
    "origin": "https://beta.example.com",
    "location": { "latitude": 31.23, "longitude": 121.47, "radiusMeters": 80 }
  },
  "storage": { "timeZone": "UTC", "money": "minor-units" },
  "settings": { "...": "各项计费设置" },
  "tables": { "...": "所选范围的完整数据表数组" }
}
```

上面是结构示意，不能直接导入。每行省略 `shop_id`，其余字段为数据库列名和原始值。导入时所有行统一归属当前经鉴权的目标店铺，不接受文件指定的 `shop_id` 或任意表／列。

事件时间、UTC 计费规则、JSON 时间轴和金额保留存储原值。货币字段使用整数分；数量、百分比等非货币数值保持原值，不统一乘除 100。已保存的历史计费版本及发布时区原样保留，不重新做 UTC 转换。API 对下载的 JSON attachment 不进行 `{data}` 包装或展示时区投影；普通业务 API 的展示时间约定不变。

文件上限 10 MiB，单行上限约 128 KiB。较大的表按 128 KiB 分块绑定，在同一事务内导入，不限制单表必须小于 1 MiB。超过限制时明确报错，不截断记录；大店铺请使用管理员的数据库备份方式。

## 导入流程与一致性

1. 在目标环境建立空店铺，选择 JSON 文件并预检。
2. 后端校验格式版本、范围内的完整字段、基本类型、整数、唯一标识、JSON、声明的外键、计费方案内容和入场配置、历史发布版本和未结会话的绑定。
3. 展示来源环境、店铺及各类记录数。目标已有玩家、业务配置、计费历史、设备、占用或店铺账号关联时，预检拒绝导入，不能覆盖或合并这些数据。
4. 店主确认后提交原文件、预检指纹和固定 `operationId`。
5. 后端再次预检，并在 D1 batch 第一条语句内校验目标状态。数据写入、配置保存与去重结果在**一个事务**内完成；任一步失败全部回滚，可以使用同一请求编号重试。

指纹包含文件、目标店铺 ID 和目标数据／设置状态。预检后改变文件、跨店铺使用指纹、修改目标设置或增加业务数据会拒绝执行。并发普通写入发生于最后一次预检与事务之间时，由事务内状态断言阻止导入。已成功的同一请求重试直接返回原结果，不再导入或转换；新请求尝试导入已有数据的店铺会被拒绝。

导出读取使用一个 D1 batch，获取一致的业务表与设置快照。恢复业务历史时仅在同一事务内暂时停用自动生成计费版本及会话绑定的两个触发器，插入原历史记录后恢复原触发器。计费历史不可变约束、UTC 写入保护与部署维护写入围栏始终保留。失败回滚同时恢复触发器，不产生缺失的计费版本。

## API

仅店主及现有授权路径中的平台管理员可访问；普通员工、其他店铺用户和 Bot Token 不可访问。每名用户、每店铺每分钟最多 10 次数据管理请求。

- `GET /api/v1/shops/:shopCode/data/export?scope=business|configuration`：原始 JSON 附件，`Cache-Control: no-store`，`Content-Disposition: attachment`；默认业务备份。
- `POST /api/v1/shops/:shopCode/data/import/preview`：`{ "backup": <文件内容> }`，返回标准 `{data}`，含 `canImport`、`counts`、`errors`、`warnings`、容量限制及 SHA-256 Base64URL `fingerprint`。结构错误为 400；语义问题放在预检结果中。
- `POST /api/v1/shops/:shopCode/data/import/apply`：`{ "backup": <同一文件内容>, "fingerprint": "...", "operationId": "UUID" }`，成功返回导入范围及各表记录数；409 表示预检不通过、目标变化、请求编号冲突或数据库约束失败；413 表示文件超限。

文件包含玩家平台标识、前台卡片 UID 和财务数据。请将文件作为敏感店铺数据保管，勿提交到代码仓库。

验证覆盖独立 D1 数据库迁移（不同账号 ID／加密密钥）、余额及历史账单原样往返、原 UTC 时间、配置复制、超过 1 MiB 的单表、请求重试、后段失败回滚与触发器恢复、并发状态变化、跨店铺权限、伪造表／字段／网页账号身份、关联失效及非法／超大文件。
