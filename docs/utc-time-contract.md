# UTC 业务时间与 UI 展示时间

内部业务时间戳、每日计费区间、新计费发布版本、优惠的日期／星期匹配和每日使用次数统一按 UTC 处理。`store.profile.timeZone` 仅决定 UI 展示时区，不再作为新计费规则的隐式业务时区。

规则编辑器按 UI 时区显示和输入，保存与预览请求转换为 `provider.timeZone='UTC'` 的规则。上海 UI 的 `10:00–次日 03:00` 对应 UTC 的 `02:00–19:00`；若 API 直接提交 UTC 的 `10:00–03:00`，上海 UI 必须显示 `18:00–次日 11:00`。时钟转换也转换规则开始日的星期和指定日期，全天规则保留原本的 24 小时窗口及封顶起点。

循环规则保持固定的 UTC 区间。在有夏令时的展示时区，其本地时间随季节变化。编辑器的预览日期决定时钟转换所用偏移；切换预览日期时重新投影显示时钟，保留原 UTC 区间。单条指定日期规则若跨越不同 UTC 偏移，需拆为独立规则或使用绝对日期时间区间，避免把同一裸时钟错误应用于不同偏移。绝对时间区间本身保持 UTC ISO 时间戳，不重复偏移。

计费日预览使用 UTC 规则在 UI 当地日所对应的 UTC 起止窗口内执行，然后投影到当地 00:00–24:00。API 按店铺时区输出带偏移的事件时间。商户账单 UI 按店铺时区、玩家账单 UI 按手机／浏览器时区，从事件 `at`、收费段 `startedAt/endedAt` 转换时间、日期和区间文字，忽略旧的后端格式化文字；切换显示时区不改变时长、金额或收费边界。

升级需应用 `0029_utc_pricing.sql` 并运行新版服务。统一平台的 `deploy:beta` 先安装维护入口与 D1 写入屏障，再原子应用 SQL；在 verify 阶段主动完成 UTC 和位置时区转换及健康检查，随后恢复业务请求。旧版本在途写入不能穿过屏障，新版计时方案还有 UTC 写入约束，避免旧代码迟到时把当地时钟错误发布为 UTC。详见 [自动维护部署](deployment.md#自动维护部署)。SQL 设置新发布的 UTC 约束；新版 SQLite 启动、Worker 首次请求以及活动账单后台读取会执行 IANA 感知的数据迁移 `utc-pricing-data-v1`。SQLite 也可单独执行 `bun run scripts/migrate-pricing-utc.ts <数据库路径>`。

`0029` 从 `utcPricingSchema` 生成，测试校验 SQL 文件与运行时 schema 严格一致，并按 D1 服务端的触发器拆分方式验证。

迁移同时转换当前方案、全部历史版本、发布的时区和历史账单时间文字／计费解释。历史发布 ID、会话绑定、已结账金额、资产账本和已支付封顶记录保持不变。同一旧方案版本若被不同业务时区的发布共享，迁移创建对应的 UTC 版本别名，并保留原收费历史身份，避免封顶重复计算。当前方案的迁移版本别名也沿用原累计身份；按偏移拆分的日期规则保留 `historyRuleId`，已有封顶额度不会因迁移或再次入场清零。日常编辑保存则创建真正的新版本，并清除迁移身份。无时间区间的固定收费保留原版本身份，不因时区转换生成无意义的别名。

历史非季节性区间转换为等价 UTC 循环区间；涉及夏令时的历史区间按实际日期展开为 UTC 绝对区间，保留 23／25 小时窗口、星期／指定日期和原封顶起点。旧会话在自然收费边界后转入固定 UTC 循环，避免在迁移时刻切断收费单位。当前编辑方案保持紧凑的 UTC 循环配置；夏令时下不能用普通 UTC 全天规则表示的指定日期改为准确的绝对区间。

废弃的 `venue.operations.timeZone` 同时归一为 UTC，展示用的 `store.profile.timeZone` 保持原值。

全部数据修改、临时开放与恢复版本防篡改触发器、完成标记在 SQLite 事务或 D1 `batch` 中一起提交。失败整批回滚；重复执行或多个 Worker 同时启动只成功提交一次，已完成的库直接跳过，不再次偏移。迁移过程中不得并行编辑旧版本；方案发布若在读取后改变，事务会拒绝这份过期转换计划。

新建或保存的计时与封顶方案均显式保存 UTC。兼容 API 中显式携带旧时区的规则在写入边界转换成 UTC；未传时区的 API 规则本身视为 UTC，不从店铺展示设置推断。

存储序列化方法 `serializePricingProviderConfig` 为未声明时区的计时／封顶方案自动补齐 `timeZone: "UTC"`，不修改时钟、星期或指定日期。向导、初始化和仓储写入无需在每个调用点手动声明 UTC。显式旧时区保留给兼容边界和历史迁移识别；新 API 保存仍先转换规则再写库，不能只改时区标签。

`provider_json.timeZone` 是 JSON 属性，`pricing_releases.time_zone` 是独立列；UTC 迁移完成后两者都固定为 UTC，但当前还有实际依赖：计费运行器会读取方案／发布的时区，部署写入保护和健康校验要求 UTC，旧 stable 升级的数据迁移需要原时区来换算历史规则。客户端规则展示可在属性缺省时按 UTC 解析，因此它们可在后续专门清理中退役，但不能只删除数据字段。尤其当前部署先执行 SQL、再转换旧数据，提前 DROP 发布时区列会丢掉转换依据。退役需同时调整迁移顺序与旧库兼容、运行器、发布触发器、部署校验和接口约定；展示用 `store.profile.timeZone` 继续保留。

完整字段用途、旧库转换依据、客户端依赖和独立 Neo 导入缺口见 [计费时区字段审计](pricing-time-zone-audit.md)。

未配置区间不会收费，也不能开始新的计费会话。已有会话可以跨越空档，在下一收费区间继续计费。账单时间轴保留收费段实际结束时间，不将闭店空档延长成收费分钟。

统一平台的店铺展示时区由店铺 WGS84 经纬度自动识别，保存到 `store.profile.timeZone`。前后端共用离线地理时区数据，返回 IANA 地区标识（例如 `Asia/Shanghai`、`America/New_York`），展示时按日期自动处理夏令时。经纬度也参与距离和地理验证；修改位置会同步更新展示时区，不修改 UTC 业务区间。独立旧版 runtime 没有店铺位置表，继续使用其展示设置。

网页版后台在「设置 → 基本资料」的地图与经纬度旁只读显示「店铺时区（随位置自动设置）」；新建店铺使用同一表单。地图选点、自动定位、手动修改经纬度都会立即重新识别时区，无需手动选择。旁边提示时区用于展示和规则编辑、计费统一使用 UTC。服务端独立按经纬度计算，忽略客户端提交的时区；位置与展示时区以 D1 原子批处理保存，保留店铺其他设置。保存后后台立即重新读取展示时区及设置。旧客户端保存营业设置时也强制采用位置时区。

统一平台首次请求先完成 UTC 计费迁移，再以 `shop-location-time-zone-v1` 原子补齐已有店铺的展示时区。完成标记与所有展示设置一起提交，失败回滚、重复执行跳过。补齐不修改 UTC 计费方案、发布或历史账单；若店铺位置在读取后改变，跳过该过期坐标的补齐，位置保存路径会写入最新的时区。

对外时间字段与 Swift／Web／Koishi 的展示分工见 [客户端时间约定](client-time-contract.md)。业务配置仍保持 UTC；响应中的 ISO 偏移只改变写法，不改变时间点或收费。
