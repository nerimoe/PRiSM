# 单方案未覆盖全天的计费验证

> 以下记录 `4400b2b` 的历史问题分析。当前已实现 [UTC 业务与 UI 转换](utc-time-contract.md)，并修正未配置区间被时间轴延长显示的问题；复现脚本现在验证修复后的行为。

改动前分析基于主仓库 `4400b2b`。当前可运行 `bun run scripts/reproduce-billing-gaps.ts` 复现；脚本使用内存 SQLite，经过真实仓储、入场、版本锁定、预览、结账和余额扣减，不依赖生产数据。JSON 输出包含收费区间、账单时间轴及显示差异。

改动前验证结果：复现脚本全部断言通过，相关 54 项测试通过；开发工具首次编译结束后，`bun test --timeout 30000` 全量 602 项测试通过。当时的测试未覆盖收费末段时间轴延长问题；现已补充回归测试。

## 结论

以下计费结果以明确持久化 `Asia/Shanghai` 时区为前提。后续截图揭示了另一条真实问题路径：页面缺省上海时区、计费却缺省 UTC，会同时造成营业时间误判和费用错误；详见 [截图时区分析](pricing-timezone-analysis.md)。

只有一个启用的 `time.priority` 方案、规则未覆盖 24 小时，是当前实现允许的配置。未命中的时段不收费，核心循环会跳到下一次规则生效或本次结束时间，并不会由于空白时段死循环或继续沿用上一条费率。

基准版本账单预览时间轴存在显示 bug（现已修复）：最后一个收费区间后面存在非营业空白时段时，仍把该区间显示为持续到预览时刻。应付金额和钱包扣款没有随这个错误增加。

若业务要求全天收费，仅配置营业区间会造成空白时间零费用；这与当前代码的非营业语义一致，需要补全规则。若业务要求到闭店自动结束会话，当前也没有此行为：会话保持进行中，次日规则生效后继续计费，直到停止或结账。

## 实测

店铺时区为 `Asia/Shanghai`；只有一个计时方案，唯一规则为每天 `10:00–22:00`，每 60 分钟 10 元，宽限 0，时段封顶 1000 元，不配置优惠或其他收费插件。

| 操作或预览时刻（店铺时间） | 实际结果 |
| --- | --- |
| 当天 09:00、22:00、23:00 新入场 | 拒绝，`PLAYER_SESSION_OUTSIDE_BILLABLE_TIME` |
| 当天 21:00 入场 | 成功，锁定计费发布版本 |
| 当天 22:00 预览 | 10 元，收费区间为 21:00–22:00 |
| 当天 23:00 预览 | 仍为 10 元，收费区间仍为 21:00–22:00 |
| 次日 09:00 预览 | 仍为 10 元，夜间空白不收费 |
| 次日 11:00 预览及结账 | 20 元，另增加次日 10:00–11:00 的 10 元 |
| 1000 元钱包结账后 | 980 元 |

管理端的日计费规则时间轴也正确返回 `00:00–10:00`、`22:00–24:00` 为 `isClosed: true`。每日区间采用起点包含、终点排除语义；起止时间相同按全天区间处理。跨午夜规则按区间起始日匹配星期及日期。

## 问题定位

`packages/application/src/bill-timeline.ts` 的 `currentTail` 判定：

```ts
const currentTail = !session.endedAt && !next && endedAt.getTime() < end.getTime();
const eventAt = currentTail ? end : endedAt;
```

注释只想兼容分钟取整后的秒级尾差，但条件没有限制尾差大小，也没有确认当前仍处于该规则内。实际收费在 22:00 停止，23:00 预览时仍将最后一个收费段的 `endedAt` 改成 23:00；次日 09:00 则改到次日 09:00。因此显示时长与收费明细不一致。此结构由 `packages/server-hono/src/views.ts` 的 `toPlayerCheckoutPreviewView` 返回给客户端。

空白期结束后，时间轴还会在前一营业段结束时显示“营业时段 → 营业时段”的切换，把中间的非营业时间省略。建议保留收费项实际起止时间，并独立表达空白期及当前状态；不要通过改写收费段末尾表达会话仍进行中。

收费侧相关位置：

- `packages/core/src/pricing-config.ts`：启用方案只要求至少一个有效规则，不要求覆盖全天。
- `packages/core/src/pricing-time.ts`：`createPriorityTimePricingProvider` 未命中规则时调用 `findNextAnyRuleActivationAfter`；`canStartPriorityTimePricingSession` 检查当前是否有有效规则。
- `packages/server/src/middleware/tenant.ts`：实际入场检查调用上述规则匹配；只有一个方案时，非营业时间被拒绝。
- `packages/application/src/player-commands.ts`：入场检查失败抛出上述业务错误，不创建会话。

## 当前计费规则摘要

同一方案只使用当前有效规则中优先级最高的一条，不同方案费用累加。按规则切段分别计算分钟和收费单位，并应用该规则窗口封顶；封顶历史按玩家、方案、规则及窗口起点累计，跨午夜并非自动重置。入场会锁定发布版本，后续修改配置不改变未结账会话。

当前代码的余数进位条件为 `leftover > 0 && leftover >= roundGraceMinutes`，即余数达到宽限即进位。例如 30 分钟 10 元、宽限 5 分钟时，未操作设备的 4 分钟为零元，5 分钟为 10 元，35 分钟为 20 元。现有 `billing-flow.md` 使用 `>` 的文字示例与此实现不一致，应以代码为准。

计费后先应用会话级资产优惠，再合并会话并应用跨方案封顶、整单优惠，最后扣钱包（赠送余额优先）。设备操作可以取消最初的免费宽限，但不会为没有命中规则的空白时间生成收费项。固定收费与收费插件是独立来源，不适用“未命中计时规则就不收费”的推断。
