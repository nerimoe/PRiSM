# API 时间与各客户端展示约定

业务计算、数据库、计费版本和循环规则统一使用 UTC。JSON 响应在传输边界将店铺事件时间投影到店铺地理时区，使用带偏移的 ISO 8601 字符串，例如 `2026-10-03T10:08:00.123+08:00`。UTC 偏移为零时可以返回 `Z`。这只是同一个绝对时间点的不同写法，不修改数据库、不重算金额，也不需要迁移历史时间戳。

```json
{
  "startedAt": "2026-10-03T10:08:00.123+08:00",
  "endedAt": "2026-10-03T11:54:00.123+08:00"
}
```

两者相减始终为 106 分钟。每个事件按其实际日期计算偏移；例如纽约夏季 `-04:00`、冬季 `-05:00`，同一段会话的起止偏移可以不同。偏移本身足以解析一个事件，不要求每张账单再附带地区时区。

## 按页面用途显示

| 页面／内容 | 展示方式 |
| --- | --- |
| 商户工作台：在店、账单、报表、历史、设备事件与资产到期 | 店铺时区；工作台明确传入店铺时区，通用列表可直接使用 API 的偏移 |
| Koishi：账单、历史、资产到期 | 使用 API 的店铺时间与偏移，不依赖 Bot 主机时区；账单注明偏移 |
| 玩家 Web／Swift：入场、结账、账单时间轴、历史及验证码／门锁密码到期 | 手机／浏览器本地时区 |
| 玩家看到的营业时段、收费规则、日预览 | 店铺时区 |
| Swift Live Activity：事件时钟、停留时长、下一事件倒计时 | 系统将绝对 Unix 时间显示为手机时区；时长与倒计时不做人工偏移 |

Swift `Date` 与 JavaScript `Date` 解析带偏移时间后得到绝对时间点，并不会保留原偏移供默认格式化使用。玩家默认采用设备时区；店铺视图显式指定店铺时区，或保留 API 字符串中的当地日期、时钟和偏移。不要给 Date 再手工加八／九小时。

商户生成兑换码时填写的到期时间也按店铺时区解释，转换为 UTC 后提交；不会误用操作员电脑的时区。

## 字段范围与兼容

- `startedAt`、`endedAt`、`settledAt`、`createdAt`、`expiresAt`、收费实际边界、报表 `from/to`、时间轴事件 `at` 等事件字段按店铺时间输出；店铺无关接口保持 UTC。
- `provider` 内的计费规则、`timeRange`、`dateTimeRange`、星期、指定日期和计费解释仍是 UTC 的业务配置；规则编辑器按店铺时区转换。用户元数据、身份值、凭据及数字 Unix 时间不进行字符串投影。
- 店铺资料／规则接口保留 IANA 地区时区，用于其他日期与循环时段的转换。仅有 `+08:00` 不能推断地理区域或未来夏令时规则。
- 计费日预览段增加 `startedAt/endedAt`，对应实际绝对边界；旧 `startLabel/endLabel` 仍表示所选店铺日期下的当地时钟，包含 `24:00`。
- `event.time/date` 和 `periodLabel` 保留为兼容展示文字。新客户端从 `event.at` 和收费段起止生成文字，避免旧文字与当前展示时区不一致。
- 排序、轨道边界及停留时长比较使用解析后的绝对时间，不能比较带不同偏移的 ISO 字符串字典顺序。

平台按请求店铺确定输出时区，设备会话与商户设备事件使用其关联店铺；旧版独立 runtime 使用店铺展示设置。响应转换是幂等的，平台转发和旧 `/rpc` 兼容路由不会重复偏移。已保存的账单快照及 SQL 时间继续保持 UTC。采用带偏移 ISO 时间的客户端也可读取旧 `Z` 格式，后端与客户端可以分别升级。

提交预览时间、资产有效期等事件字段时，接口同时接受 `Z` 和 `±HH:mm`，解析成绝对时间后执行业务并保存为 UTC。结账确认可原样提交预览响应中的 `previewedAt`。
